# ADR-0002 — meco-faces as a separate service

Status: **accepted, 4 Sep 2026**; extended with `POST /embed`, 4 Sep 2026; extended with `POST /objects`, 5 Sep 2026. Research: [`../research/subject-aware-cropping.md`](../research/subject-aware-cropping.md). Plan: [`../plans/faces-and-subject-aware-crop.md`](../plans/faces-and-subject-aware-crop.md) phase 2. Builds on [ADR-0001](0001-analytic-solver-over-search-based-crop.md), which made a detected face one producer of Subject Boxes among several.

## Context

The solver wants faces. Getting them means ONNX Runtime, a model file and a session that has to be created before the first answer — about 116 MB of dependency and a load meco has no other use for.

meco is a scale-to-zero container. It boots for a `list_templates` call, for the console's first page, for every MCP exchange. Every one of those boots would carry the face stack if the face stack lived in meco's image, and almost none of them would ask for a face.

The detector is also the part most likely to be replaced. YuNet is a 230 KB MIT model chosen on licence as much as accuracy; a better one under an acceptable licence is a plausible upgrade, and so is a hosted API. What must not move when that happens is meco's own API.

## Decision

Face ML runs in **its own container image and its own service**, `meco-faces`, with four routes — `POST /detect`, `POST /embed`, `POST /objects` and `GET /health` — and no state at all.

- **In: image bytes. Out: JSON.** It never reads Blob, never knows a Person, holds no secret but `MECO_TOKEN`, and returns every number as a fraction of the image so nothing it says depends on a resolution.
- **A face's box is `{ x, y, width, height }`**, not the `{ x, y, w, h }` of the plan's shorthand. The plan is a sketch and the merged code is the authority: [ADR-0001](0001-analytic-solver-over-search-based-crop.md)'s `SubjectBox` in `src/crop-solver.ts` already spells it this way, and a detected face becomes a `SubjectBox` the moment meco reads it. Aligning the wire with the type it feeds means no rename at the boundary, and no response that carries `subjectArea.width` beside `faces[].box.w`. Do not "correct" it back to the plan.
- **Detecting and embedding are two calls, not one.** `POST /embed` takes the image bytes again, plus the faces `/detect` already found as `?faces=<json>`, and answers `{ prints: [[512 floats]] }` in the caller's order. meco does not want a Face Print for every face in a photograph — it caches an Annotation per image and embeds only the faces that might be a Person — so a route that always did both would run the expensive half on faces nobody asked about. The faces ride in the query string because the body is the photograph. That caps how many one call can carry: measured at 632 encoded bytes per face passing `/detect`'s whole answer through, 443 passing only the landmarks, so Node's default 16 KB of request line and headers is reached at about 25 faces — past which the platform answers 431 before meco-faces sees anything. `/embed` therefore reads `landmarks` and nothing else, so a caller with a crowd can drop the rest.
- **`POST /objects` finds what is not a face, and says nothing about what it means.** A helmet is not a face, and on a race track that is most of the photographs: measured on 32 on-track karting shots, YuNet puts a box on the leading driver's head in 9. So a second detector — D-FINE-N, COCO-pretrained, 15 MB — answers `{ objects: [{ label, score, box }] }` in the vocabulary it was trained in. COCO has no kart, so a kart comes back as `motorbike`; the word is wrong and the box is right, and this service is not the place to fix the word. Deciding that a `motorbike` and the `person` sitting on it are one Subject is framing policy, and framing policy lives in meco beside every other producer, where it is arithmetic that needs no service and no model to test. That is the third paragraph of the Context made concrete: this route can be swapped for a different detector answering different labels without meco's idea of a kart moving at all. The class *index* the model uses is deliberately not on the wire, for the same reason.
- **The object model must have no Objects365 in it.** D-FINE publishes `*_obj365` and `*_obj2coco` checkpoints that score better than the COCO-only ones and are the variants its own README recommends for fine-tuning. Objects365 states it is *"available for the academic purpose only"*, and D-FINE's README carves those checkpoints out of its own Apache-2.0 grant by name. COCO is not a second one — its annotations are CC BY 4.0 with no non-commercial clause. So the rule outlives this particular model: **an Objects365 lineage disqualifies a detector here however good it is**, and the lineage is usually only in the checkpoint's name. Beyond the licence on the weights, prefer an export that ships the licence *text*, because §4 requires it to travel with a derivative and this image redistributes one. `packages/faces/models/LICENCE-dfine.txt` is that attribution.
- **A third route, not a third model on `/detect`.** The two models answer different questions and a caller wants one or the other: a portrait has no use for a `motorbike` box, and an on-track photograph has no face to find. Splitting them means the object path never loads EdgeFace and the face path never loads D-FINE — a session create each, on a container that scales to zero and pays its cold start on a real request. Measured: cold to a served face detection is unchanged by the third model.
- **A Face Print is unit length, and carries no identity.** meco-faces normalises so a comparison is a dot product and every Face Print is on the same scale, and it returns no name: the gallery a print is matched against lives in meco, and this service cannot see it.
- **The EdgeFace weights are exported once, offline, and committed.** `packages/faces/scripts/export-edgeface.py` pins `otroshi/edgeface` at commit `ce86851c` and the checkpoint's SHA-256, and refuses to finish unless the ONNX output still matches the PyTorch output. The `.onnx` is in the repository and copied into the image, like YuNet: a container that downloads a model at boot is a container that fails when the download does. The weights are CC BY-NC-SA 4.0 against BSD-3 code — an accepted MVP risk, still owed its own ADR.
- **Alignment is `sharp.affine()` and twenty lines of arithmetic, not OpenCV.** The five landmarks are fitted onto InsightFace's `arcface_dst` by a closed-form similarity transform. The one non-obvious part is that libvips sizes the output canvas from the linear part of the matrix alone and rounds that corner **to nearest** (`VIPS_ROUND_INT`), not down — using a floor puts the whole warp one pixel out whenever a rotation makes the corner land on a negative fraction. Measured after the fix, on landmarks placed by a known similarity so the fit has no residual to hide behind: every landmark within **0.15 px** of its reference point and the eyes within **0.05 px**. On a real face, where the fit does leave a residual, the pixels land within **0.19 px** of where the transform says they will.
- **meco stays the only public API.** meco calls meco-faces; nobody else does.
- **Both services live in one Vercel project**, declared as two entries under `services` in `vercel.json` and separated by a rewrite: `/faces/(.*)` to `meco-faces`, `/(.*)` to `meco`. This closes the plan's open question 2, on a preview deployment rather than on the documentation: both services build, and `GET /faces/health` returns the model and the ONNX Runtime version while `GET /health` still answers from meco. The fallback of a second project with a `FACES_URL` env var is not needed.
- **The rewrite passes the path through unchanged** — the deployment proves it, since `/faces/health` reaches the faces container still wearing the prefix. The faces app therefore mounts its routes at both `/` and `/faces`, and answers the same way behind the rewrite, behind a second project, or under plain `docker run`.

## Consequences

- **meco's cold start is unchanged.** The face stack is only ever loaded by a container that was started to find a face. meco-faces' own cold and warm figures live in [`../../DEPLOY.md`](../../DEPLOY.md) and are re-measured whenever a model is added, rather than restated here where they would go stale.
- **A PyTorch environment is a prerequisite for changing the model, and only for that.** Nothing in the service, the tests or the image needs Python. The export needs a Python that PyTorch publishes wheels for, which a laptop on 3.14 does not have; the reference Face Prints it writes to `fixtures/faces/edgeface-reference.json` are what let `pnpm test:embed` keep checking ONNX against PyTorch without one.
- **Two images to build and keep green**, and a second `pnpm` workspace package. `pnpm deploy` is what keeps meco's own dependencies — takumi, react, pdf-lib — out of an image that renders nothing.
- **A network hop per detection**, inside one project. The cost is bounded by the rule that every Source Image is analysed once and the Annotation is cached under the image's hash.
- **Both models are replaceable behind three endpoints.** A different detector or a different recognition model, or a hosted API for either, is a change to one service and no change to meco.
- **One token, two services.** `MECO_TOKEN` is set on both. `/detect` and `/embed` require it; `/health` does not, because a liveness probe that needs a secret cannot be used by the platform deciding whether the container is alive.
- **The faces image is built from a root-level `Containerfile`**, which is the only name left once two Vercel constraints are applied: a service `entrypoint` must have the basename of a Dockerfile or a Containerfile, and the build context is the entrypoint's own directory rather than the service `root`, so the file cannot sit beside the package it builds — the install needs the workspace lockfile at the repository root. `Dockerfile.vercel` is meco's. Both constraints cost a failed deployment each to find; they are written down in [`../../DEPLOY.md`](../../DEPLOY.md).
- **`vercel.json` rewrites are ordered**, and meco's `/(.*)` catches everything. The faces rule has to stay above it, and anything meco ever serves under `/faces` would now be shadowed.
- **The detect knobs stayed out.** `/detect` takes an image and nothing else: no score or NMS threshold in the query string. The defaults are the ones the fixtures are calibrated against, and a tunable surface on a route only meco calls is a promise with no one to keep it.
- **A single project means a single deployment.** Both services are built and promoted together and neither can be rolled back on its own. The documentation says Vercel "builds each service separately"; whether a meco-only change avoids rebuilding faces is not stated anywhere, and in practice layer caching does the work — do not rely on it. Splitting them later is a `vercel.json` edit plus a `FACES_URL` env var, which is why meco reaches the service by configuration rather than by a hardcoded path.
- **Two limits inherited from the platform.** Vercel's services documentation carries a "Permissions Required: Services" badge, so the capability may be plan-gated on another account even though it works on this one; the second-project fallback above is what to reach for if it ever is. And container images do not support Secure Compute or Static IPs, so neither service can sit behind either.
